# 0023 휴지통 만료 카드의 분산 락과 청크 삭제

- 상태: 채택
- 날짜: 2026-11-28
- 관련: `JECT-84`, [ADR 0015](0015-product-card-and-rediscovery-schema.md), [ADR 0022](0022-soft-delete-board-card-links.md)

## 배경

삭제된 상품 카드는 30일 뒤 영구 파기 대상이다. 여러 서버 인스턴스의 동일 스케줄이 겹칠 수 있고, 대량 삭제를 한 트랜잭션에서 처리하면 행 잠금과 롤백 비용이 커진다. 카드 이미지 파일은 다른 카드가 함께 참조할 수 있으며 Object Storage 삭제는 DB 트랜잭션에 참여하지 않는다.

## 결정

스케줄러는 PostgreSQL `pg_try_advisory_xact_lock`으로 정리 작업 전용 락을 비차단 획득한다. 획득하지 못하면 이번 주기를 건너뛴다. 바깥 트랜잭션은 락만 유지하고, 각 청크는 별도 `REQUIRES_NEW` 트랜잭션에서 만료 카드 ID를 `deleted_at, id` 순으로 최대 설정 크기만큼 읽고 삭제한다. 조회와 삭제 모두 DB 시각 기준 `is_deleted = TRUE AND deleted_at <= CURRENT_TIMESTAMP - INTERVAL '30 days'` 조건을 적용한다. 삭제 전에 해당 카드의 활성 이미지 미러링 작업 행을 잠가 기존 워커와 잠금 순서를 맞춘다. 삭제는 `product_cards`를 대상으로 하며 연결·태그·이벤트·미러링 작업은 FK cascade에 맡긴다.

카드가 참조하던 `files` 행과 Object Storage 객체는 이 배치에서 삭제하지 않는다. 공유 참조 여부 검사와 스토리지 실패 후 재시도를 포함한 고아 파일 회수는 기존 `JEC-10`의 별도 작업으로 둔다.

## 영향

청크가 성공한 뒤 다음 청크가 실패해도 앞선 삭제는 커밋된다. 다음 실행은 남은 만료 카드부터 다시 처리한다. 배치 프로세스가 실행되지 않는 기간에는 파기가 지연될 수 있지만 휴지통 조회와 복구는 만료 카드를 즉시 제외한다. 락 유지 동안 DB 연결 하나와 청크용 연결 하나가 필요하다. 실행 주기·시간대·청크 크기·활성 여부는 [운영 문서](../operations.md#휴지통-만료-상품-정기-삭제)에서 관리한다.
