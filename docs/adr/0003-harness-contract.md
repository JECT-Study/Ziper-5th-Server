# 0003 검사 정책의 신뢰 경계와 적용 범위

- 상태: 채택, 소유자 쓰기 권한과 필수 소유자 승인 설정 확인; CODEOWNERS는 기본 브랜치 병합 후 적용
- 날짜: 2026-11-01

## 배경

작업 규칙만으로는 업무 계층의 예외 처리나 문서 검토 누락을 반복해서 막기 어렵습니다. 반대로 후보 PR이 정책 검사기를 바꾼 뒤 자기 자신을 승인하면 검사의 신뢰를 유지할 수 없습니다.

## 결정

정책은 Checkstyle AST 검사, ArchUnit 운영 코드 검사와 정상·위반 fixture, 문서·PR 정책 검사로 나눕니다. 문서 지도는 목적·변경 계기·ADR 이력의 진입점이며 `config/harness/doc-policy.json`은 유지 문서와 경로별 검토 문서를 정의합니다. `scripts/check-harness-policy.py --repo .`는 문서 지도 링크와 누락·중복·경로 이탈, 중앙 catch 허용 목록의 범위를 검사합니다. PR 검사는 연결된 문서의 검토 링크와 구체적인 영향 없음 이유를 요구합니다. 장기 결정만 ADR과 문서 지도의 실제 변경을 요구합니다. 기능 구현 상세와 사용자 이야기의 E2E 증거는 PR에 남깁니다.

정책 CI는 기본 브랜치의 스크립트와 경로별 문서 정책을 사용하고 후보 트리, 변경 경로 JSON과 PR 본문을 데이터로 읽습니다. 후보의 검사 스크립트를 정책 승인 근거로 실행하지 않습니다. 첫 도입은 기본 브랜치에 새 검사기가 없으므로 불변 SHA `4aa71645b050c95a9dcdd3d072af9cba4ca6daa6`의 기존 구조 검사와 새 검사기의 자체 테스트, 사람의 검토를 사용합니다. 새 자동 정책은 첫 병합 이후 적용됩니다.

CODEOWNERS는 정책 파일과 검사 경로의 소유자를 지정합니다. 기본 브랜치의 CODEOWNERS, 소유자의 쓰기 권한과 필수 리뷰 보호 설정이 갖춰져야 승인 요구가 작동합니다. 첫 도입 PR과 워크플로 자체 변경은 사람의 검토가 필요합니다. `pull_request`에는 비밀 값이나 쓰기 권한을 주지 않습니다.

## 대안

지침과 사람의 리뷰만 유지하는 방식은 반복 위반을 자동으로 차단하지 못해 채택하지 않았습니다. 후보 PR의 검사기로 정책을 승인하는 방식은 검사기 변경으로 우회할 수 있어 제외했습니다. 실행 샌드박스는 별도 실행 환경과 권한 설계가 필요하므로 이번 도입 범위에 포함하지 않았습니다.

## 영향과 한계

업무 `service`·`controller`의 catch는 AST로 금지하고, 불가피한 예외는 중앙의 정확한 파일·줄 범위 허용 목록과 PR 이유·소유자 승인으로 관리합니다. 전역 오류 처리와 외부 I/O 경계의 catch, 자원 정리 구문은 허용합니다. ArchUnit은 계층 의존과 명시한 세션 API·사용자 정의 예외 경계를 검사합니다. 모든 상태 저장이나 동적 동작을 증명하지는 않습니다.

검사는 문서를 읽고 이해했는지, PR의 증거가 사실인지 보장하지 않습니다. 문서 자동 주입, OS 샌드박스와 작업 명세 기반 실행은 이번 범위에서 구현하지 않습니다. 파일별 소유권, 격리 worktree와 최종 포맷 1회는 협업 규칙이며 자동 차단 기능으로 기록하지 않습니다.
