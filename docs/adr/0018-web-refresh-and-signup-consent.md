# 0018 웹 Refresh 쿠키와 소셜 가입 약관

- 상태: 채택. 운영 도메인과 실제 브라우저 연동은 배포 시 검증
- 날짜: 2026-11-21

## 배경

웹은 브라우저 스크립트가 읽을 수 없는 방식으로 세션을 유지해야 합니다. 네이티브 앱과 공유 확장은 기기의 보안 저장소에 Refresh Token을 저장할 수 있어야 합니다. 소셜 계정을 검증하는 것만으로는 Ziper 서비스 이용약관과 개인정보 수집·이용에 동의했다는 기록이 생기지 않습니다.

## 결정

일반 API는 Access Token을 Bearer 헤더로 인증합니다. 웹은 Access Token을 메모리에 두고, 로그인과 가입의 Refresh Token 전달 방식으로 HttpOnly·Secure·SameSite=Lax 쿠키를 선택합니다. 쿠키는 API 호스트와 인증 경로에 한정합니다. 회전과 로그아웃은 기존 DB 세션 계약을 공유하며, 웹 쿠키 모드에서는 명시적 Origin 허용 목록과 opt-in 헤더를 모두 확인합니다. 네이티브 클라이언트는 Refresh Token을 본문으로 보내고 받습니다.

기존 소셜 회원은 검증 후 로그인합니다. 신규 소셜 회원에게는 회원이나 세션을 생성하기 전에 10분 유효한 일회용 가입 토큰을 발급합니다. 가입 토큰의 해시와 검증된 소셜 계정 정보를 PostgreSQL에 저장합니다. 필수 약관에 동의한 요청만 토큰을 소비할 수 있으며, 토큰 소비와 회원·기본 보드·세션 생성은 한 트랜잭션에서 처리합니다. 같은 소셜 계정이나 이메일의 중복 가입은 계정과 이메일별 잠금으로 막습니다.

이메일·소셜 신규 가입에서 필수 약관의 동의 시각을 저장합니다. 필수 약관 동의를 검증해 생성하던 기존 이메일 회원은 생성 시각을 사용합니다. 동의 근거가 없는 기존 소셜 회원의 필수 약관 시각은 비워 두고 상태 조회에 그대로 반영합니다. 로그인 성공과 세션 갱신 응답은 DB에 기록된 약관 상태를 반환합니다.

## 대안

- 웹 서버를 통해 모든 API를 중계하는 BFF 방식은 브라우저 호출을 단일 출처로 만들 수 있습니다. 웹 서버와 백엔드 사이의 추가 요청이 필요하므로 앱과 웹이 백엔드를 직접 호출하는 구성을 선택합니다.
- Access Token까지 쿠키에 넣으면 일반 상태 변경 API도 쿠키 기반 CSRF 방어 범위에 들어갑니다. 쿠키 사용은 Refresh Token에 한정합니다.
- 자체 서명한 가입 토큰은 DB 발급 행을 줄일 수 있습니다. 토큰을 일회용으로 소비하고 검증된 계정 정보와 동의 결정을 트랜잭션으로 연결하기 위해 DB 티켓을 사용합니다.

## 영향과 한계

운영 웹과 API는 각각 `https://app.ziper.cc`와 `https://api.ziper.cc`에서 같은 사이트로 접속할 수 있어야 합니다. 웹과 앱에서 새 소셜 가입 계약을 지원한 뒤 서버 변경을 배포합니다. 약관 버전과 동의 변경 이력의 저장은 별도 결정으로 남깁니다.

[ADR 0010](0010-oauth-login-and-token-lifecycle.md)과 [ADR 0016](0016-email-password-signup.md)의 소셜 자동 가입 및 필수 약관 저장 규칙은 이 결정으로 대체합니다.
