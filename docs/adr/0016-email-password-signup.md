# 0016 이메일·비밀번호 가입, 인증 흐름 소비와 OAuth 이메일 중복 처리

- 상태: 채택; 실제 메일 수신 번호로 진행하는 가입 E2E와 운영 배포는 미검증
- 날짜: 2026-11-18

필수 약관 시각 기록과 소셜 가입 절차는 [ADR 0017](0017-web-refresh-and-signup-consent.md)에서 변경했습니다.

## 배경

[ADR 0009](0009-email-verification-delivery.md)와 [0012](0012-email-verification-lockout.md)는 가입 전 이메일 인증까지만 결정했고 회원 가입과 인증 코드 소비는 후속 작업으로 남겼다. 이메일 가입 화면은 이메일 인증 → 비밀번호·약관 동의 → 닉네임 순서로 진행하며, 가입 완료 후 바로 홈으로 이동한다. `users.password_hash`와 `auth_codes.consumed_at` 컬럼은 이미 있지만 비밀번호 해시 방식과 인증 흐름을 가입에 연결하는 규칙이 없었다.

## 결정

`POST /api/v1/auth/email/signup`은 인증을 마친 `flowId`, 비밀번호, 닉네임, 약관 동의를 받아 회원을 만들고 자체 Access/Refresh JWT를 발급한다. 회원·기본 보드·세션 생성과 `auth_codes.consumed_at` 기록은 하나의 DB 트랜잭션에서 처리한다. `flow:`, `email:`, `nickname:` advisory lock을 이 순서로 잡아 이메일 인증 API와 같은 잠금 키를 공유한다. 소비한 흐름은 확인·재전송·가입 모두 `EMAIL_FLOW_INVALID`로 거부한다. 인증 후 30분이 지난 흐름도 같은 오류로 거부해 인증부터 다시 시작하게 한다.

비밀번호는 Spring Security `DelegatingPasswordEncoder`(기본 BCrypt, `{bcrypt}` 접두사)로 해시해 저장한다. 원문과 확인 값은 저장하거나 기록하지 않는다. 비밀번호 확인 일치 여부는 클라이언트가 판정한다. 서버 규칙은 영문·숫자·특수문자를 각각 1자 이상 포함한 공백 없는 ASCII 출력 문자 8~64자이며, BCrypt 72바이트 입력 한도를 넘지 않도록 상한을 둔다.

이미 가입된 이메일(OAuth 가입 포함, 대소문자 무시)은 인증번호 발급·재전송과 가입 모두에서 `EMAIL_ALREADY_REGISTERED`(`409`)로 거부한다. 발급 시 거부하면 발급 행을 만들지 않고 메일도 보내지 않는다. 필수 약관(서비스 이용약관, 개인정보 수집·이용)은 동의 여부만 검증하고 별도로 저장하지 않으며 동의 시각은 `created_at`으로 간주한다. 선택 마케팅 동의는 `users.marketing_agreed`에 저장한다.

OAuth 자동 가입은 이메일이 같은 기존 회원(이메일 가입 포함)과 자동으로 연결하지 않고 `EMAIL_ALREADY_REGISTERED`(`409`)로 거부한다. 클라이언트는 이 코드로 기존 가입 수단으로 로그인하도록 안내한다. 프로바이더 이메일은 앞뒤 공백을 지우고 소문자로 정규화해 저장·비교한다. 같은 소셜 계정의 동시 첫 로그인은 `oauth:{provider}:{providerId}` advisory lock으로 직렬화해 뒤 요청이 먼저 가입된 회원으로 로그인하게 하고, 이메일이 있으면 이메일 가입과 같은 `email:` 잠금을 잡은 뒤 중복을 확인한다. advisory lock은 `global/persistence`의 `AdvisoryLockRepository`로 공유한다.

## 대안

- 가입 시점에만 이메일 중복 검사: 계정 존재 노출은 줄지만 비밀번호·닉네임까지 입력한 뒤 실패하므로 선택하지 않는다. 노출은 출처당 시간당 20회 발송 한도로 제한한다.
- 가입 성공 시 토큰 없이 회원 ID만 반환: 화면이 가입 완료 후 바로 홈으로 이동하므로 별도 로그인 호출이 필요해져 선택하지 않는다.
- 필수 약관 동의 시각 컬럼이나 이력 테이블 추가: 동의 증빙은 강해지지만 현재 기획 범위를 넘어 스키마 변경 없이 검증만 한다. 약관 개정·철회 관리가 필요해지면 새 ADR로 결정한다.
- 이메일이 같으면 OAuth를 기존 계정에 자동 연결: 프로바이더 이메일의 소유 검증 수준이 제각각이라 계정 탈취 위험이 있어 선택하지 않는다. 소유를 증명한 뒤의 명시적 연결은 이메일 로그인과 다중 OAuth 연결 스키마(현재 `users.oauth_connect`는 회원당 하나)가 필요하므로 후속 결정으로 남긴다.
- 대소문자 무시 고유 인덱스(`lower(email)`) 추가: DB 최종 방어선이 되지만 기존 데이터 점검과 마이그레이션이 필요해 이번에는 애플리케이션 정규화와 잠금으로 처리한다.
- `BCryptPasswordEncoder` 직접 사용: 저장 값에 알고리즘 식별자가 없어 이후 해시 방식을 바꾸기 어려우므로 위임 인코더를 사용한다.

## 영향과 한계

`users.email` 고유 제약은 대소문자를 구분하므로, 정규화 이전에 저장된 대소문자 혼합 이메일이나 잠금을 거치지 않는 경로의 쓰기는 DB가 막지 못한다. 같은 이메일을 다른 사람이 먼저 소셜 가입에 사용하면 이메일 소유자는 이메일 가입을 할 수 없다. OAuth 자동 닉네임 생성은 `nickname:` 잠금을 공유하지 않아 이메일 가입과 같은 닉네임을 동시에 고르면 고유 제약 위반이 `5xx`가 될 수 있다(자동 닉네임 형식 `Ziper#####`와 겹칠 때만 해당). 이메일·비밀번호 로그인은 이 결정에 포함하지 않으며 후속 작업에서 다룬다.
